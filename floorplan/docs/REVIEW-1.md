# Review round 1 — findings (2026-11-24)

Five independent reviewers plus an end-to-end scan simulation reviewed the first integrated build. Each reviewer's findings were then checked by an adversarial verifier that tried to refute them. The run was stopped before the last verifications finished; those findings are marked **unverified** and must be re-checked before fixing.

Verdicts: **confirmed** = real defect; **uncertain** = needs a device to settle; **unverified** = verifier did not run; **refuted** = not a defect.

Verified sections: Capture flow, AR layer, Core math, App. **Not verified:** Product / UX and Accuracy simulation (the run was stopped first). Every reviewer numbered its findings AR-1, AR-2, … so ids repeat across sections — refer to findings as `<section> <id>`.


## Capture flow

### AR-1 — A skipped ceiling is saved as the default height and looks measured everywhere after saving

- **Severity:** minor (reviewer: major) · **Verdict:** confirmed
- **Where:** `floorplan/app/src/main/java/com/oroplex/floorplan/ui/capture/CaptureViewModel.kt:106`

- **Problem:** RoomDraft.toRoom() writes `ceilingHeight = ceilingHeight ?: settings.defaultCeilingHeight`, and saveAndScanNext/saveAndFinish save that Room. The model marks an unmeasured ceiling with null (Model.kt: "null if not measured"), and the rest of the app relies on that: EditorPanels.kt:127 shows "Not set", EditorDialogs.kt:160 says "Not measured yet", PdfExporter.kt:200 prints a dash, and Measurements.room only computes volume and wall area when the height is non-null. The "(estimated)" flag only exists in the draft (ceilingMeasured) and is lost on save, even though DESIGN.md says Skip is "marked estimated".
- **Failure scenario:** The user taps Skip on CEILING in every room. Review shows "8' 0" (estimated)". After saving, the editor shows Ceiling 8' 0" as if it were measured, and the PDF room schedule prints 8' 0" for every room. Wall area and volume, which contractors use for paint and drywall quotes, are computed from the assumed 8 ft. In a house with 9 ft ceilings those numbers are about 11 % low and nothing marks them as assumptions. Later changing the project's default ceiling height does not update these rooms. Tape calibration also scales the fake value (RoomOps.scale), producing odd heights like 8' 2".
- **Suggested fix:** In toRoom() keep `ceilingHeight = ceilingHeight` (null when skipped). ReviewPanel.reviewStats already falls back to the default for display. If an 'estimated' flag must persist, add an explicit field to Room instead of storing the default.

- **Verifier:** The code does what the finding says. RoomDraft.toRoom() (CaptureViewModel.kt:106) writes `ceilingHeight ?: settings.defaultCeilingHeight`, and both save paths save that Room (saveAndScanNext line 752, finishSession line 832). The draft only treats null as 'skipped' (skipCeiling line 365 sets null/false), but the stored model uses null to mean 'not measured' (Model.kt:116). Every consumer after the save then shows the assumed value as if it were measured: EditorPanels.kt:127 prints the value instead of "Not set", EditorDialogs.kt:160 never says "Not measured yet", and PdfExporter.kt:200 prints it in the room schedule instead of a dash. RoomOps.scale (RoomOps.kt:163) multiplies it by the calibration factor, for example 2.4384 x 1.025 = 2.499 m, about 8' 2.4". Room has no 'estimated' flag, so the "(estimated)" label from DESIGN.md exists only in ReviewPanel and is lost on save. Changing the default later cannot update these rooms. I am downgrading from major because Measurements.room's wallArea and volume are never shown or exported anywhere in :app (grep finds no consumer), so the claim about '11 % low paint/drywall quotes' is overstated. The real impact is that an assumed height looks measured in the editor, the PDF schedule and the JSON. Area and dimensions are not affected, and the user knowingly tapped Skip.

- **Fix notes:** CaptureViewModel.kt, RoomDraft.toRoom(): change to `ceilingHeight = ceilingHeight?.takeIf { ceilingMeasured }`, so a skipped ceiling is saved as null. Update the RoomDraft.ceilingHeight KDoc (line 67), which currently says the default is used on save. ReviewPanel.reviewStats (lines 100-101) already falls back to settings.defaultCeilingHeight plus "(estimated)" for display, so review is unchanged. captureWall (line 416) already passes only a measured ceiling. Update the CEILING copy in CaptureControls.kt:91 ("Skip to use 8' 0\""), for example to "Skip (you can enter it later in the editor)", so the editor's later "Not set" does not contradict it. Tests: add a CaptureViewModelTest that skips the ceiling, saves, and asserts the stored room's ceilingHeight is null. If the product wants the default to persist instead, add an optional field to Room (for example `ceilingEstimated: Boolean = false`, @Serializable with a default) and show it as '(est.)' in EditorPanels, EditorDialogs and PdfExporter. Do not store the bare default.


### AR-2 — "Re-lock floor" is undone by auto-lock within about 1 s, and auto-lock can pick a raised surface

- **Severity:** major (reviewer: major) · **Verdict:** confirmed
- **Where:** `floorplan/app/src/main/java/com/oroplex/floorplan/ui/capture/CaptureViewModel.kt:329`

- **Problem:** relockFloor() only sets floorY = null and step = FIND_FLOOR. On the next frames onFrame() (lines 254-279) sees the same frame.floorY, which is still confident (area ≥ 1 m²), and calls acceptFloor() again after AUTO_LOCK_STABLE_NS (1 s). So the same surface locks again before the user can aim and tap Lock floor. That surface comes from FloorSelection.select (FloorTracker.kt:74): the LARGEST upward plane at least 0.5 m below the camera, not the lowest one. acceptFloor's raised-surface check compares against that same best floor, so it cannot catch this. Re-lock is therefore broken in exactly the case it exists for.
- **Failure scenario:** In a kitchen the user sweeps the phone (held at about 1.5 m) over a 2.5 m² granite island at 0.9 m. It is detected before the floor, which is partly hidden by cabinets, and becomes the largest plane. It is 0.6 m below the camera, so it qualifies, and after 1 s "Floor locked." fires at island height. The user notices and taps Re-lock floor, then reads "Floor found. Hold still for a moment, or tap Lock floor". About 1 s later the island locks again. Every FloorPoint (corner taps, wall-base taps, door edges) is then the ray hitting Y = 0.9 m instead of the real floor. A corner 3 m away lands about 1.7 m from the camera, so the room is badly wrong. The ceiling also reads 0.9 m too low and gets rejected (below MIN_CEILING), so measuring it never succeeds.
- **Suggested fix:** After relockFloor() (and after any auto-lock the user rejected), turn off auto-lock for the rest of FIND_FLOOR, or ignore candidates within tolerance of the rejected Y, so the user locks with the reticle. In FloorSelection prefer the lowest qualifying plane above a minimum area (or reject candidates when a lower qualifying plane exists) instead of the largest.

- **Verifier:** I traced the frame loop. relockFloor() (lines 329-334) only resets the candidate and sets floorY=null with step=FIND_FLOOR. On the next frame, onFrame (lines 258-279) passes every gate: step FIND_FLOOR, floorY null, not busy. frame.floorY comes from FloorTracker.current, which is sticky (FloorTracker.kt:56) and does not depend on where the user aims. It is still the same plane, area >= 1 m², so it becomes the candidate and acceptFloor(y) runs after AUTO_LOCK_STABLE_NS = 1 s. acceptFloor's raised-surface check (lines 317-322) compares y against frame.floorY, which is the same value, so the difference is 0 and the check cannot fire. FloorSelection.select (FloorTracker.kt:74-81) returns the LARGEST TRACKING upward plane at least 0.5 m below the camera, not the lowest. A kitchen island (0.9 m, about 2.5 m²) or a queen bed top (0.55-0.65 m, about 3 m²) with the phone at about 1.5 m qualifies, and can outsize a partly occluded floor during the first second after area reaches 1 m². The only way out is to aim at the floor and tap Lock floor within about 1 s of tapping Re-lock, which the user is not doing because CEILING had them aiming up. Re-lock is available only in CEILING (CaptureControls), which is exactly when this matters. Two sub-claims are wrong. With an 8 ft ceiling and a 0.9 m island the ceiling reads 1.54 m, which is above MIN_CEILING = 1.5 and above the CeilingSampler minY of floorY+1.5, so it is accepted with a wrong value rather than rejected. And a floor corner 3 m away with the phone at 1.5 m lands about 1.2 m away horizontally, not 1.7 m. The geometry is still badly wrong either way, so the conclusion stands.

- **Fix notes:** (1) CaptureViewModel: add state for a rejected floor, for example `private var rejectedFloorY: Double?` or a CaptureUiState field `autoLockFloor: Boolean = true`. In relockFloor() record the previous floorY (or turn auto-lock off). In onFrame, skip auto-lock while it is off, or while `abs(y - rejectedFloorY) <= ~0.10`. Clear the flag in acceptFloor on success and in attach() when the session resets. In acceptFloor, also refuse a manual lock within tolerance of the rejected Y and post a message, unless the user deliberately confirms. (2) CaptureControls.stepInstruction FIND_FLOOR/CONFIDENT: when auto-lock is off, say "Aim at open floor and tap Lock floor" instead of "Hold still for a moment". (3) FloorTracker.kt FloorSelection.select: prefer the lowest qualifying candidate with a minimum area (for example >= 0.5 m²), or keep the largest but replace it with a lower candidate (more than 0.2 m lower, area >= 0.5 m²) when one exists. Update the FloorTracker KDoc and the FloorSelection JVM tests. This also lets acceptFloor's MAX_ABOVE_BEST_FLOOR check catch manual locks onto islands and beds. Keep the minimum area so small spurious low planes, such as reflections on glossy floors, cannot win.


### AR-3 — No way back from REVIEW except "Redo room", which throws away every wall

- **Severity:** minor (reviewer: minor) · **Verdict:** confirmed
- **Where:** `floorplan/app/src/main/java/com/oroplex/floorplan/ui/capture/CaptureViewModel.kt:569`

- **Problem:** undo() ignores REVIEW (`else -> Unit`). ReviewPanel only offers Save & scan next, Save & finish and Redo room, and Redo resets observations, corner taps and openings. System Back from REVIEW opens the 'Discard this room?' dialog. So once the user taps Done in OPENINGS they cannot return to remove one bad wall or add a forgotten door.
- **Failure scenario:** A user captures 6 walls and 2 doors and taps Done. Review shows the warning "Corner 4 forms a very sharp spike; check walls 5 and 6", caused by a bad last wall. Their only choices are to save a wrong room or tap Redo room and re-capture all 6 walls and both doors. Fixing it in the editor means dragging corners by hand. The same happens if they remember a window at review time.
- **Suggested fix:** Let undo()/Back in REVIEW return to OPENINGS with the solve and openings kept. From there the existing Undo and Reopen room steps can roll back further.

- **Verifier:** undo() handles only WALLS, CORNERS and OPENINGS. REVIEW falls into `else -> Unit` (line 569). ReviewPanel offers only Save & scan next, Save & finish and Redo room. redoRoom (lines 722-743) rebuilds the RoomDraft with only the id, method, ceiling, type and name kept, so observations, cornerTaps and openings are dropped. In CaptureScreen, BackHandler/requestExit (lines 135-141) opens the discard dialog because hasRoomInProgress is true in REVIEW. So after tapping Done there is no way to go back one step. The editor can partly compensate: the wall panel has Add door/window and Insert corner, and corners can be dragged. But it cannot drop a bad wall observation and re-solve without it. This is a real UX gap, minor.

- **Fix notes:** CaptureViewModel.undo(): add `CaptureStep.REVIEW -> mutableState.update { it.copy(step = CaptureStep.OPENINGS) }`, keeping the draft (solve, openings, name, nameEdited, type) unchanged. From OPENINGS the existing Undo/Reopen room path (reopenRoom re-solves) can roll back further. finishOpenings keeps a user-edited name, so going back and forth is safe. ReviewPanel: add a "Back to doors & windows" TextButton bound to a new additive ReviewActions member (for example `backToOpenings()` that calls vm.undo()), and implement it in BoundCaptureActions (CaptureScreen.kt). Optionally make CaptureContent's BackHandler call vm.undo() when ui.step == REVIEW instead of opening the discard dialog, so the explicit close (X) button stays the discard path. Add a CaptureViewModelTest: REVIEW -> undo -> OPENINGS with the openings and solve intact.


### AR-4 — The floor can only lock from detected planes, so a floor without plane detection blocks the whole flow

- **Severity:** minor (reviewer: minor) · **Verdict:** uncertain
- **Where:** `floorplan/app/src/main/java/com/oroplex/floorplan/ar/MeasurementEngine.kt:234`

- **Problem:** The floor can only lock from ARCore planes. LockFloorSampler uses `input.reticle?.plane` (planes only) or `input.floor` (FloorTracker, planes only). Auto-lock needs frame.floorY, which also comes from planes. The reticle's floor-ray fallback needs floorY too. DepthPoint and feature-point hits under the reticle, which exist even when plane detection fails, are never used, and the user cannot enter the height manually. Every later step needs floorY.
- **Failure scenario:** On a job site with polished concrete or glossy large-format tile, ARCore finds no upward plane. Lock floor fails every time with "No floor found yet...", the reticle stays red, and the user can never reach CEILING, WALLS or CORNERS. Leaving the screen and drawing the room by hand is the only way out.
- **Suggested fix:** In LockFloorSampler, fall back to the median Y of DepthPoint or feature-point hits under the reticle over a few frames, provided they are at least 0.3-0.5 m below the camera. Optionally offer a 'floor is N below the phone' estimate from the camera height.

- **Verifier:** The code claims are accurate. LockFloorSampler (MeasurementEngine.kt:234-249) accepts only `input.reticle?.plane` of type HORIZONTAL_UPWARD_FACING, or `input.floor` (FloorTracker, planes only). The auto-lock in onFrame needs frame.floorY, which also comes from FloorTracker. HitTesting.resolveReticle's floor-ray fallback needs floor?.y from that same tracker. DepthPoint and Point hits are returned by resolveReticle but never used for locking, and nothing lets the user enter a floor height. Whether the failure scenario happens in practice is a device question: ARCore must find no upward plane at all while still giving usable DepthPoint or feature hits on the same surface. Depth-from-motion and feature points also struggle on uniform glossy surfaces, and in-plane reflections can mislead both. The flow is not a dead end: the user gets a message and can draw the room in the editor, which is DESIGN fallback (d). This is a robustness gap rather than a proven bug; it needs a device to judge how common it is.

- **Fix notes:** If addressed, change MeasurementEngine.kt LockFloorSampler from a one-frame sampler into a short multi-frame sampler. Keep the current plane and tracker paths first. As a fallback, collect `input.reticle?.hit?.world?.y` when `reticle.fromHitTest` is true and the hit is a DepthPoint or Point (SurfaceKind.DEPTH or FEATURE_POINT), over about 10-15 frames. Require the median Y to be at least 0.5 m below the camera (match FloorSelection.MIN_DROP_BELOW_CAMERA) and the MAD to be under about 3 cm. Return MeasureResult.FloorLocked(median). CaptureViewModel.acceptFloor already rejects heights too close to the camera. The auto-lock should stay plane-only. Optionally mention in the FIND_FLOOR failure message that Lock floor works while aiming at textured floor near the feet.


### AR-5 — Rooms scanned into an already calibrated floor are saved unscaled while the floor still says it is calibrated

- **Severity:** minor (reviewer: minor) · **Verdict:** confirmed
- **Where:** `floorplan/app/src/main/java/com/oroplex/floorplan/ui/capture/CaptureViewModel.kt:752`

- **Problem:** saveAndScanNext and finishSession (line 832) upsert the raw AR room into the floor. They ignore floor.calibration, which FloorOps.calibrate set after scaling every room that existed then. The editor wall panel (EditorPanels.kt:220) still shows "Floor calibrated ×f from a tape measurement" for every wall, including the new room's. A later recalibration multiplies all rooms again, so the earlier rooms end up scaled twice.
- **Failure scenario:** The user calibrates the Main Floor ×1.025 from a tape-measured wall, then goes back and scans a forgotten bathroom. The bathroom is about 2.5 % smaller relative to its neighbours, yet its wall panel says the floor is calibrated. If they then calibrate from a bathroom wall, the earlier rooms end up ×1.05 overall. Room sizes on the export no longer agree with each other.
- **Suggested fix:** When saving into a floor with a calibration, either apply RoomOps.scale(room, calibration.factor, …) and say so, or mark the calibration as not covering the new room (e.g. warn in review and in the wall panel) so the user recalibrates on purpose.

- **Verifier:** FloorOps.calibrate (RoomOps.kt) scales every room that exists at that moment and stores a composed `Calibration(factor = previous * factor, ...)` on the Floor. The capture save paths never read floor.calibration: saveAndScanNext (line 752) and finishSession (lines 831-834) upsert the raw AR room. grep finds no use of `calibration` under ui/capture. EditorPanels.kt:220 shows "Floor calibrated ×f" for any wall on the floor, including walls of the unscaled new room. The double-scaling math checks out. After rooms A-C were scaled x1.025, a raw room D has an edge about 2.5 % short. Calibrating from D gives factor about 1.025, which is applied to all rooms, so A-C end up about x1.0506 overall while D is about x1.025. Going back to scan a forgotten room after calibrating is a normal workflow. Manually drawn rooms (drawRoom) have typed dimensions and correctly stay unscaled.

- **Fix notes:** Preferred fix, in CaptureViewModel inside both repository.update transforms (saveAndScanNext and finishSession): read `val f = floor.calibration?.factor?.takeIf { it.isFinite() && it > 0 && abs(it - 1) > 1e-9 }` and upsert `RoomOps.scale(room, f, Vec2.ZERO)`. Use one fixed origin, the AR world origin, for every room of the session so rooms scanned together stay aligned with each other. Anchor corrections in finishSession are computed in the raw AR frame. For a room pre-scaled about the origin, the matching correction is `RigidTransform2(t.angle, t.translation * f)`, because S∘T∘S⁻¹ = R p' + f·t. So scale the correction translations for rooms saved under a calibration before calling applyCorrections, or apply corrections to raw rooms first and scale afterwards. Post a review or snackbar note such as "Floor calibration ×f applied". Alternative if scaling is unwanted: add an additive field to Calibration (for example `roomIds: List<String> = emptyList()`) and show the EditorPanels.kt:220 line only for covered rooms, with a 'not covered by calibration' hint otherwise. Note that FloorOps.calibrate composes factors, so a later recalibration would still double-scale covered rooms; the scale-on-save approach avoids that.


### AR-6 — Common configuration changes recreate the activity and end the AR session mid-scan

- **Severity:** minor (reviewer: minor) · **Verdict:** confirmed
- **Where:** `floorplan/app/src/main/AndroidManifest.xml:24`

- **Problem:** configChanges lists only orientation|screenSize|screenLayout|keyboardHidden. A uiMode change (Samsung scheduled dark mode at sunset), a keyboard or navigation change (a Bluetooth laser meter connecting in HID-keyboard mode), smallestScreenSize, density or fontScale all recreate MainActivity. ArSessionGate keeps its session in plain `remember`, so a new ARCore session is created. CaptureViewModel.attach() (line 227) then resets floorY, the draft and sessionRoomIds. Rooms already saved in the old session never get their anchor corrections, and new rooms land in an unrelated coordinate frame. After process death the VM is new, so attach() doesn't show the 'AR session restarted' message and the room in progress is lost without notice.
- **Failure scenario:** Late afternoon the user has saved 3 rooms and captured 4 walls of a 4th. At sunset the phone switches to dark mode. The camera restarts at 'Find the floor', the 4 walls are gone, and the next rooms no longer line up with the first three on the plan, so the floor no longer assembles itself.
- **Suggested fix:** Add uiMode|keyboard|navigation|smallestScreenSize|density|fontScale|locale|layoutDirection to configChanges for this AR-only activity (Compose handles the resulting configuration updates). On session restart, apply the old controller's anchorCorrections() to sessionRoomIds before clearing them, since close() keeps the last poses for that purpose.

- **Verifier:** The manifest (line 24) handles only orientation|screenSize|screenLayout|keyboardHidden. Any other configuration change recreates MainActivity. The CaptureViewModel survives (NavBackStackEntry store), but ArSessionGate's `remember` state does not: the old runner is disposed and its holder and controller closed, then ArSessionFactory.create makes a new session with a new controller sessionId. CaptureContent's LaunchedEffect calls vm.attach(newController). attach() (lines 227-247) sees a different non-null sessionId and resets floorY, step, draft and sessionRoomIds, posting the restart message only if a room was in progress. The VM never keeps the old controller, so the saved session rooms never get anchorCorrections, and later rooms are in an unrelated frame. One caveat on the trigger: AOSP's UiModeManagerService normally defers scheduled (automatic or custom) dark-mode switches until the screen is off, and the AR view sets keepScreenOn. So 'sunset mid-scan' probably shows up only after the user next locks and wakes the phone. That still recreates the activity and kills the session, where a plain pause and resume would have kept the frame. Samsung multi-window or pop-up view (smallestScreenSize), a hardware keyboard or HID laser meter (keyboard, navigation), and density or font scale changes are other triggers. The process-death point is a separate, inherent limit (the draft is not persisted). It is real but needs no AR-6 fix beyond an optional message.

- **Fix notes:** AndroidManifest.xml MainActivity: change configChanges to `orientation|screenSize|smallestScreenSize|screenLayout|keyboard|keyboardHidden|navigation|uiMode|density|fontScale|locale|layoutDirection`. The app is Compose-only with a Light-only XML theme and no isSystemInDarkTheme use, and AndroidComposeView updates LocalConfiguration and Density on onConfigurationChanged, so no other code is needed. Optionally also keep the old session's corrections: in CaptureContent add `DisposableEffect(controller) { onDispose { vm.onControllerDisposed(controller) } }`, which snapshots safeCorrections(controller) for sessionRoomIds while the old session is ending, and have attach() persist them through repository.update + applyCorrections before clearing sessionRoomIds. Guard it so it never runs after finishSession has already applied corrections, using `finished` or a per-session 'corrected' flag, or rooms would be shifted twice. Compose disposes child effects before ArSessionContent's runner.dispose(), and close() keeps the last poses, so anchorCorrections() still answers.

That skips vm.exit(), the 'Discard this room?' confirmation and the finishSession anchor corrections.

The user presses Back expecting to return to the scan. The capture screen closes at once, the room in progress (walls and openings) is lost without confirmation, and the rooms saved earlier in the session stay uncorrected.

- **Verifier:** ArSessionContent (ArCaptureHost.kt:205-213) keeps content(controller) composed and then composes ArSetupErrorScreen(CAMERA_UNAVAILABLE, onBack = onExit) after it. ArMessageScreen installs `BackHandler(onBack = onBack)` (ArErrorScreens.kt:55). Because it is registered after CaptureContent's BackHandler (CaptureScreen.kt:141), the OnBackPressedDispatcher gives it priority. The order also survives stop/start, since lifecycle observers re-add the callbacks in registration order. onExit is CaptureScreen's onDone (line 73), that is nav.popFrom(entry). So system Back, or the overlay's Back button, pops the screen without vm.exit() or finishSession. The overlay appears when Session.resume throws CameraNotAvailableException or the renderer reports camera loss, for example another app holding the camera in multi-window or after returning from a call. Pressing Back on an error screen to mean 'leave' is reasonable, but skipping the confirmation and the corrections is a real defect, minor.

- **Fix notes:** ArCaptureHost.kt ArSessionContent: once `runner.started` is true, do not let the overlay own Back. Add an additive parameter to ArSetupErrorScreen/ArMessageScreen, for example `handleSystemBack: Boolean = true`, and pass `!runner.started` so the overlay's BackHandler is disabled and CaptureContent's BackHandler (requestExit -> discard dialog -> vm.exit) handles Back. For the overlay's Back TextButton while in session, call `LocalOnBackPressedDispatcherOwner.current?.onBackPressedDispatcher?.onBackPressed()` so it goes through the same handler. The AlertDialog is its own window, so it shows above the overlay. vm.exit -> finishSession -> safeCorrections works on a paused controller because anchorPoses keeps the last snapshot. This keeps the ArCaptureHost signature unchanged, as DESIGN.md requires. Keep onExit for pre-session errors (permission, install, session creation).


**Reviewer notes:** Checked and correct: (1) Overlay geometry. The GLSurfaceView (AndroidView fillMaxSize) and the CaptureOverlay Canvas fill the same Box, so canvas size equals ArFrameState.viewportWidth/Height (edge-to-edge applies to both). setDisplayGeometry uses the GL viewport, so the projection matrix, hitTest(center) and the reticle drawn at canvas center agree. ## AR layer (ARCore/OpenGL)

### AR-1 — Floor = largest upward plane, so beds, tables and islands can become the floor and auto-lock

- **Severity:** major (reviewer: major) · **Verdict:** confirmed
- **Where:** `floorplan/app/src/main/java/com/oroplex/floorplan/ar/FloorTracker.kt:74`

- **Problem:** FloorSelection.select returns the LARGEST TRACKING HORIZONTAL_UPWARD plane whose center is at least 0.5 m below the camera (lines 70-81, used at line 56). With the phone at chest height (1.3-1.5 m), a bed top (0.5-0.65 m), a dining table (0.75 m) or a kitchen island or counter (0.9 m) all pass the 0.5 m test. Whichever plane is biggest right now becomes ArFrameState.floorY/floorArea. CaptureViewModel.onFrame auto-locks that height once its area is >= 1 m2 and has stayed steady for 1 s. acceptFloor's 'raised surface' guard (CaptureViewModel.kt:317-322) compares the candidate against frame.floorY, which is that same furniture plane, so it cannot catch this. LockFloorSampler (MeasurementEngine.kt:244) also falls back to the same estimate. After the first room the lock is kept for the whole session.
- **Failure scenario:** Bedroom with a patterned duvet and low-texture carpet, or a glossy floor. ARCore finds the bed (about 3 m2 at y = 0.55 m) before the floor plane grows past it. ### SIM-3 — TOO_NOISY gate compares PER-POINT noise to 3 cm, so every capture beyond ~2.2 m fails and the 4 m / TOO_FAR guidance is unreachable

- **Severity:** major (reviewer: major) · **Verdict:** unverified
- **Where:** `floorplan/core/src/main/kotlin/com/oroplex/floorplan/core/fit/WallEstimator.kt:49`

- **Problem:** maxRms = 0.03 is compared (L190-191) against max(inlier RMS, 1.4826*MAD of points within 10 cm), i.e. the per-sample perpendicular noise. It should be the uncertainty of the fitted line, which shrinks with ~500-1000 inliers. With depth-from-motion noise sigma = 5 mm + 1.2 % * d (the brief's model, consistent with DESIGN's 'several cm at 3 m'), per-point noise exceeds 3 cm at about 2.1 m. maxRange = 6 m and the TOO_FAR message 'Move within about 4 m (13 ft)' contradict this: users get 'Hold steady, add light, or move closer' at 2.5 m. The gate is also what lets the thin grazing side-wall fit of SIM-1 through while it rejects the correct wall.
- **Failure scenario:** Distance sweep, flat wall head-on, 30 captures per distance. Default success is 100 % up to 1.5 m, 80 % at 2.0 m, and 0 % at 2.5, 3.0, 3.5 and 4.0 m (all TOO_NOISY). The same captures with maxRms 0.10 have line offset median 2-5 mm and max 12 mm at 4 m. With a range-adaptive band the max is 4.7 mm and the angle at most 0.62 deg. In (a), standing at the room's centre point, 64 of 340 captures fail on the first try (Living/Kitchen 30/60). Test distanceSweep_wallsWithin4mAreAccepted is @Ignore'd for this.
- **Suggested fix:** Gate on noise relative to the expected sigma at the measured range, and on the fitted line's standard error (offset and direction), not on absolute per-point sigma. If far captures should be discouraged (they do weaken large-room accuracy, see the SIM-5 what-if), do it explicitly with TOO_FAR at ~2.5-3 m and an accurate message, and align maxRange and the TOO_FAR text.


### SIM-4 — Far-corner warnings fire on a third of accurate scans and feed the reorder penalty

### SIM-5 — Residual error is dominated by whole-room rotation times the patch-to-corner lever arm; the fixed 2.5 cm fit band inflates per-wall direction error

- **Severity:** minor (reviewer: minor) · **Verdict:** unverified
- **Where:** `floorplan/core/src/main/kotlin/com/oroplex/floorplan/core/solve/RoomSolver.kt:110`

- **Problem:** Squaring rotates every wall about its observed patch midpoint (L112) onto ONE dominant axis. That axis is the 4-theta mean of per-wall directions weighted by confidence * extent (L110, weight at L324). Each capture sees only a 0.2-1 m patch. Its fitted direction is refined inside the fixed 2.5 cm band (WallEstimator inlierThreshold L43), so once sigma_perp exceeds the band (above ~1-2 m) the refinement stays anchored to the 2-point RANSAC hypothesis. The resulting direction error is 2-3x what the points support: p95 1.1-1.7 deg at 2-4 m versus 0.4-0.6 deg with a range-adaptive band. The room rotates by the weighted mean of these errors, and each corner moves by theta times the distance from its patch to the corner. Weighting by extent favours far or oblique captures, which have the poorest directions.
- **Failure scenario:** (a) Living/Kitchen s2/jitter: the 2.25 m wall 3 is 24 mm too long while every wall offset is under 3.6 mm. The cause is rotation 0.204 deg times the 4.35 m lever arm to the corner. Overall rotation reaches 0.35 deg in (a) and 0.64 deg in (b2). In (f), hallway lengths are within 2.9 mm but corners are off 18.8 mm (0.34 deg over 5.4 m). In (c), calibration is exact (pure scale about the floor centre, factor within 0.17 % of 1/1.02), yet calibrated Living walls are 28 mm off because the scan without any scale error is already 21 mm off. What-if accepting far captures: Living reaches 52 mm and 0.5 deg rotation, driven by 3.2-3.9 m captures at 25-70 deg incidence whose 2-3 m extents dominate the weights. Tests cleanWalls_everyWallWithin2cm and scaleError_calibratedFloorWithin1cm are @Ignore'd for this.
- **Suggested fix:** Weight the dominant direction by direction precision (roughly inliers * extent^2 / sigma^2) instead of confidence * extent. Refine per-wall direction with a noise-adaptive band or IRLS rather than the fixed 2.5 cm band. Consider guiding users to take a second capture near the other end of long walls; merge already unions extents and averages direction, and in (e1) a retake halved the Living/Kitchen max error to 12 mm.
